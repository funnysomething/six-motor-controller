# Run Testudo detection on the camera AI processor

The IMX500 runs the neural network in this workflow. The Pi receives its output
tensors, decodes detections, and draws the preview. This differs from NCNN, where
the Pi CPU runs the network. Actual stream and inference rates need measurement
on your Pi; camera offload is not a guarantee of a particular FPS.

Ultralytics currently supports YOLO11n and YOLOv8n for IMX500, and explicitly marks
YOLO26 as unsupported. You must train a supported architecture using your existing
images and boxes. Renaming the YOLO26 model or converting its NCNN files will not
make it compatible.

## 1. Train YOLO11n on your Mac

From the repo root in your training environment:

```sh
python testudo_training/train.py \
  --data datasets/testudo/data.yaml \
  --model yolo11n.pt \
  --device mps \
  --batch 4 \
  --imgsz 640 \
  --epochs 100 \
  --name testudo_imx500
```

This is a new training run. Your YOLO26n results remain available. The script
prints the trained `best.pt` location. Do not add `--export-ncnn` for this path.
Use 50 epochs for an initial experiment if desired, then assess validation quality.

## 2. Export the trained weights on Linux

Ultralytics IMX export requires **Linux, Python 3.9+, and Java 17+**. This export
cannot run directly in your macOS Python environment. Use a Linux environment
supported by the Sony converter and its Python dependencies. An existing Linux
PC or VM is appropriate; do not assume every ARM container has compatible wheels.
The Pi may be constrained by conversion dependencies and memory.

Copy or clone this complete repo to Linux, including `datasets/testudo` and the
trained weights in `testudo_training/runs/`. The prepared YAML resolves image paths
relative to its own directory without machine-specific edits. Export uses
representative images for INT8 calibration, so the YAML alone is insufficient.
Use your real Testudo data rather than a generic calibration dataset.

In a Linux virtual environment with `testudo_training/requirements.txt` installed
and Java 17+ available:

```sh
python testudo_training/export_imx500.py \
  --weights testudo_training/runs/testudo_imx500/weights/best.pt \
  --data datasets/testudo/data.yaml \
  --imgsz 640
```

The exporter may install additional dependencies. Conversion can take time. The
resulting `best_imx_model` directory contains `packerOut.zip`, `labels.txt`, and
conversion artifacts. Retain the complete directory. This is an IMX500 export,
not an NCNN export. A compatible export is required before the next step can run.

## 3. Install the camera runner dependencies on the Pi

Use current 64-bit Raspberry Pi OS and the detected IMX500 camera. Close other
camera processes. The camera must appear in `rpicam-hello --list-cameras`.

```sh
sudo apt update
sudo apt install imx500-all python3-venv python3-opencv python3-picamera2
python3 -m venv --system-site-packages raspberry_pi/.venv-imx500
source raspberry_pi/.venv-imx500/bin/activate
python -m pip install --upgrade pip
python -m pip install 'git+https://github.com/SonySemiconductorSolutions/aitrios-rpi-application-module-library.git'
```

Sony modlib handles deployment and network output decoding. Its platform packages
must match your Pi OS/libcamera version. Follow the upstream installation guide
if installation reports a missing platform dependency. Use this separate
environment to preserve your NCNN environment. Network and first-run packaging
dependencies may also be needed during initial deployment.

## 4. Copy the model and run

Copy the **whole IMX export directory** from your Linux conversion environment to
the Pi. For example, from that machine:

```sh
scp -r testudo_training/runs/testudo_imx500/weights/best_imx_model YOUR_USER@PI_ADDRESS:~/six-motor-controller/testudo_training/runs/testudo_imx500/weights/
```

On the Pi desktop, from the repo root, with `.venv-imx500` activated:

```sh
python raspberry_pi/imx500_detect.py --model-dir testudo_training/runs/testudo_imx500/weights/best_imx_model --seconds 120
```

The default requests 16 camera FPS, following the Ultralytics deployment example.
`--fps` changes the request, not the network's achievable inference rate. The
program logs stream FPS without claiming each displayed frame has new detections.
Use `--conf 0.4` to adjust the confidence threshold. Press Ctrl+C to stop.
Over SSH without a desktop, add `--headless` to log detections without a window.
Initial packaging and firmware/model loading can take several minutes.

Inspect boxes at different distances and angles, then test scenes with Testudo
removed. Quantization can affect accuracy. The new camera runner does not control
motors or replace the NCNN benchmark. Real hardware testing is required; local
simulated tests cannot confirm camera deployment or speed.

## Export stops after the INT8 warning

INT8 quantization is required by IMX500. A warning that enables it is expected;
it does not identify the cause of a later failure. The exporter now explicitly
requests INT8 using the option supported by the installed Ultralytics version.

Run `./scripts/vision/export-imx500.sh` again. The launcher streams output without
Python buffering and saves it under `testudo_training/export_logs/` inside the
repo, including the process return code. It reports termination by signal and
enables Python's native crash traceback. The exporter prints host, package, Java,
and memory information before conversion. No existing partial export is deleted.

If it reports SIGKILL or status 137, inspect the kernel log immediately:

```sh
sudo dmesg -T | tail -n 80
```

Look for an out-of-memory entry naming the export process. SIGKILL alone does not
prove memory exhaustion. If confirmed, use a Linux machine or VM with more memory
and the same repo/dataset to convert the trained weights, then copy the generated
IMX directory back to the Pi. No retraining is needed for moving the export step.

For SIGILL, SIGSEGV, or SIGABRT, preserve the export log and exact package versions;
these indicate a native process crash and should not be treated as proof of low
memory. An ordinary Python exception now includes its full traceback in the log.
